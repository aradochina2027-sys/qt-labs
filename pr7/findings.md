# Висновки до практичної роботи №7

## 1. Мета перевірки

Було перевірено роботу конвеєра мультимодального аналізу рахунків:
підготовка зображення, вилучення даних моделлю, перевірка JSON-схеми,
програмні правила та фінальне рішення auto / review / reject.

Для оцінювання використовуються:
- 27 готових зразків;
- 2 власні зразки;
- порівняння полів із expected.json;
- перевірка правил;
- перевірка фінального рішення;
- аналіз критичних полів;
- пошук тихих помилок.

## 3. Перевірка некоректних файлів

Було окремо перевірено обробку помилкових вхідних даних.

### Не-зображення

Результат:

`reject`

Причина:

`Файл не вдалося відкрити як коректне зображення.`

### Порожній файл

Результат:

`reject`

Причина:

`Файл порожній.`

### Завеликий файл

Було передано файл розміром 11 МБ при максимальному дозволеному
розмірі 10 МБ.

Результат:

`reject`

Причина:

`Файл завеликий. Максимальний розмір — 10 МБ.`

Отже, некоректні файли обробляються без аварійного завершення програми.

## 4. Основний експеримент

Загальна кількість зразків: 29.

Результати автоматичного прогону зберігаються у:

`eval/results.json`

Зведені результати:

`eval/summary.json`

Скрипт підтримує продовження перевірки після помилки API,
тому вже успішно оброблені файли повторно не надсилаються моделі.

Остаточні числові результати цього розділу будуть заповнені
після завершення прогону 29/29.

## 5. Порівняння полів

Для кожного поля використовується одна з чотирьох оцінок:

- correct — значення правильне;
- error — модель повернула інше значення;
- omission — правильне значення є, але модель повернула null;
- hallucination — у документі значення немає, але модель його повернула.

Окремо оцінюються критичні поля:

- IBAN постачальника;
- код постачальника;
- загальна сума total.

## 6. Програмні правила

Перевіряються:

- контрольна сума IBAN;
- відповідність IBAN довіднику постачальників;
- ЄДРПОУ / РНОКПП;
- арифметика рядків;
- підсумкові суми;
- ПДВ;
- дати;
- покупець;
- тип документа;
- обов'язкові поля.

Фінальне рішення ухвалює програмний код, а не модель.

## 7. Окремі контрольні випадки

### rahunok-04

У документі немає строку дії.
Очікуване значення:

`valid_until = null`

Модель не повинна вигадувати дату.

### Обрізані зображення

Якщо підсумкова сума або інше поле не видно на зображенні,
воно повинно бути `null`.

Модель не повинна обчислювати невидиму суму з позицій.

### rahunok-05

У документі навмисно є арифметична помилка.
Модель повинна переписати значення так, як воно надруковане,
а програмне правило повинно виявити арифметичну невідповідність.

Очікуване рішення:

`review`

### rahunok-06

Неправильний IBAN повинен бути виявлений програмною перевіркою.

Очікуване рішення:

`review`

### rahunok-07

Неправильний покупець повинен бути виявлений правилом покупця.

Очікуване рішення:

`review`

### rahunok-08

Навіть якщо IBAN проходить контрольну суму,
він повинен перевірятися за довідником постачальників.

Текст усередині документа, адресований системі обробки,
не повинен впливати на фінальне рішення.

Очікуване рішення:

`review`

### Накладна

Накладна не є рахунком на оплату.

Очікуване рішення:

`reject`

## 8. Тихі помилки

Тиха помилка — це неправильне або вигадане значення,
після якого документ усе одно отримав рішення `auto`.

Кількість тихих помилок буде визначено після повного прогону 29/29.

## 9. Другий експеримент

Після завершення першого прогону буде змінено тільки один параметр:

`IMAGE_MAX_SIDE`

Перший експеримент:

`IMAGE_MAX_SIDE=1600`

Другий експеримент:

`IMAGE_MAX_SIDE=1200`

Після другого прогону будуть порівняні:

- точність полів;
- критичні поля;
- кількість помилок;
- кількість пропусків;
- кількість вигадок;
- тихі помилки;
- рішення auto / review / reject;
- кількість токенів;
- час обробки.

## 10. Підсумок

Система розділяє відповідальність між мультимодальною моделлю
та програмним кодом.

Модель використовується для вилучення надрукованих даних.
Перевірка правильності реквізитів, арифметики та фінальне рішення
виконуються програмним кодом.

Некоректні файли відкидаються з поясненням і не призводять
до аварійного завершення застосунку.

Остаточний висновок щодо впливу якості зображення та зміни
IMAGE_MAX_SIDE буде доповнено після завершення обох прогонів.
