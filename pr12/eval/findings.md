
# Практична робота №12
## Оцінювання та безпекове тестування AI-функцій

### 1. Мета роботи

Побудувати систему автоматизованого оцінювання AI-функцій, перевірити якість відповідей, стійкість до prompt-ін'єкцій, правильність використання інструментів та узгодженість оцінок AI-судді з оцінками людини.

### 2. Об'єкти тестування

1. ПР11 — генерація чернеток відповідей клієнтам магазину «Сузір'я».
2. ПР8 — AI-помічник із доступом до інструментів роботи із замовленнями.

### 3. Тестові набори

Для генератора чернеток підготовлено 30 прикладів:

- Normal — 4.
- Edge — 8.
- Negative — 8.
- Adversarial — 10.

Для помічника ПР8 підготовлено 15 прикладів, зокрема два власні adversarial-сценарії g14 і g15.

Окремо підготовлено 4 held-out приклади для фінальної перевірки.

### 4. Автоматичні перевірки

Реалізовано перевірки:

- Мова відповіді — language.
- Відсутність вигаданих чисел — numbers_from_facts.
- Захист від розкриття системної інструкції — no_system_prompt.
- Правильність аргументів інструментів — args_match.
- Заборонені виклики — tools_forbidden.
- Дозволені виклики — tools_allowed.
- Вміст тексту — contains_all, not_contains, regex.
- Оцінювання за рубрикою — judge.

Виконано 17 модульних тестів.

Результат: 17/17, OK.

Mock-прогін:

Водночас mock-помічник не виконав жодного реального виклику інструментів.

Тести проводилися з підставними відповідями моделі та контрольованими викликами сервісу.

### 10. Виявлені ризики

У ПР8 реалізовано перевірку власника замовлення, але customer_id для /api/ask надходить із тіла HTTP-запиту.

Перевірка існування customer_id не є автентифікацією.

Тому в реальній системі потрібні:
- Автентифікація користувача.
- Отримання customer_id із захищеного сеансу.
- Авторизація операцій на рівні сервісу.

Крім того, навчальний ендпоінт /api/reset не має обмеження доступу. У робочому середовищі його необхідно захистити або вимкнути.

Виявлено ризик недостатньої перевірки підстав для повернення: алгоритм перевіряє наявність характерних слів у зверненні, але це не повноцінне підтвердження обставин.

### 11. Обмеження

- Реальний API генератора повертав rate_limit.
- Повне порівняння v3 та v4 на реальній моделі не завершено.
- Mock-прогони не замінюють тестування реальної генерації.
- Тести інструментів не замінюють перевірку автентифікації.
- Негативна калібрація AI-судді має малу вибірку.
- Held-out набір підготовлено, його фінальний результат буде додано окремо.

### 12. Висновок

Створено тестовий конвеєр для двох AI-функцій, реалізовано автоматичні перевірки та оцінювання AI-суддею.

Локальні тести підтвердили працездатність перевірок і здатність виявляти задані порушення в синтетичних сценаріях.

Під час аналізу ПР8 виявлено ризик підміни customer_id через відсутність автентифікації на веб-рівні.

Посилено системну інструкцію ПР11, однак її перевага на реальній моделі не підтверджена через обмеження API.

Для повної оцінки якості необхідно повторити реальні експерименти після відновлення доступу до провайдера.
